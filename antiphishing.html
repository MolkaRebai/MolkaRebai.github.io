Building a Smart Anti-Phishing Extension: URL Classification with LightGBM and Chrome MV3

A learning project write-up — how I trained a 4-class URL classifier and shipped it as a real-time Chrome extension, including the honest gap between the research and what actually runs in the browser today.

The problem

Traditional phishing defenses lean on blacklists: a URL gets reported, someone verifies it, it's added to a list, and browsers block it from then on. That works, but only after the first victim. New phishing domains are cheap to register and typically live for hours to days, so a static list is always a step behind.

The alternative is to judge a URL on its own structure — the way it's shaped, not whether it's been seen before. A URL like secure-paypal-login.tk/verify?id= carries signal in its shape alone: a suspicious keyword, an unusual TLD, a query string, no real brand domain. I wanted to see how far that idea could go if trained on a large, real-world dataset, and whether it could run cheaply enough to sit directly in the browser.

What I built

A 4-class classifier — benign, phishing, malware, defacement — trained on 651,191 labeled URLs, using 21 structural features extracted from the raw URL string alone: IP-address usage, @ symbol presence, hyphen count, subdomain depth, shortening-service detection, suspicious keywords, URL and hostname length, and so on. No page content, no network requests, no rendering — just the string.

label datasets (malicious_phish.csv, phishing_urls.csv)
   → feature extraction (21 features, pure string/regex logic)
   → LightGBM multiclass classifier (gradient-boosted trees)
   → classification_report + confusion matrix
   → joblib.dump("lgb_model.pkl")

I trained with LGBMClassifier(objective='multiclass', boosting_type='gbdt'), evaluated with a full classification report and confusion matrix per class, and saved the fitted model with joblib. On the held-out test set, the model reached:

Phishing is the hardest class, and that tracks with intuition: phishing pages increasingly mimic real login flows almost exactly, so the URL-only signal is weaker there than for something structurally distinctive like a defacement URL. Malware's recall (0.84) tells a similar story — some malware URLs simply don't look different from benign ones at the string level.

Turning it into a Chrome extension

The extension is Manifest V3: a background service worker (background.js) intercepts navigation via webNavigation.onBeforeNavigate, a content script (content.js) scans every <a> tag on the page (including ones added dynamically, via a MutationObserver) and asks the background worker to classify each link's destination, and declarativeNetRequest blocks confirmed-malicious navigations by redirecting to a warning page.

webNavigation.onBeforeNavigate
   → extractFeatures(url)          — 21 features, in JS
   → classify → {class, confidence, score}
   → confidence > 0.85 & (phishing|malware) → declarativeNetRequest block + redirect
   → otherwise, suspicious → inline warning badge on the link in content.js

Blocking rules are temporary by design — each one auto-expires after 30 seconds, since phishing infrastructure rotates domains quickly and a permanent rule list would just grow stale.

The honest gap: the trained model vs. what ships in the browser

This is the part I think is worth being upfront about, because it's the single most important engineering fact about the current version.

The 95%-accuracy numbers above belong to the real, trained LightGBM model (lgb_model.pkl), evaluated offline in Python against the test set. That model does not run inside the browser. LightGBM is a tree ensemble with no native JavaScript runtime, and I haven't yet built the export step (something like m2cgen, ONNX.js, or a hand-rolled tree-traversal compiled to JS) that would let the browser execute the actual fitted trees.

What ships today in background.js is a hand-tuned heuristic that approximates the model's behavior: the same 21 features are extracted client-side, but instead of running them through the real trees, each class gets a weighted linear score against a small number of hand-picked features (phishing weights suspicious_words and shortening_service heavily, for example), and the class with the highest score wins. model_info.json's feature_importances_normalized array — the real importances the trained model reported — is loaded but currently only kept as a fallback reference; it isn't the thing actually driving predictions per-request yet.

So the honest framing is: the research model is real and its 95% figure is real. The in-browser model is a lightweight, hand-tuned stand-in inspired by that research, not a client-side port of it — yet. Calling the deployed version "the LightGBM model running in your browser" overstates what's currently true, and closing that gap (a genuine model export, not a rules proxy) is the highest-value next step for this project.

Making sure blocks are real threats, not noise

Given that the shipped classifier is a heuristic, false positives were the first thing I had to guard against — blocking github.com because it has a hyphen and a query string would make the extension unusable.

  • Known-safe allowlist. A short list of major domains (Google, GitHub, Wikipedia, Microsoft, etc.) is checked first and short-circuits everything else.
  • Single-indicator dampening. If only one of the three strongest signals (IP-address use, a shortening service, a suspicious keyword) fires and overall confidence is still low, the URL is downgraded to "suspicious" rather than blocked outright — one signal alone isn't proof.
  • Short-URL leniency. Very short URLs with low confidence default to benign, since most of the 21 features need a reasonably long string to be meaningful in the first place.
  • Two-tier response. Only high-confidence (>0.85) phishing/malware predictions trigger an actual navigation block; everything in the "suspicious" band gets an inline warning badge on the link instead — the person can still choose to proceed.

What I'd improve next

  • Actually port the trained model. Export lgb_model.pkl's trees (via m2cgen, a WASM build, or ONNX.js) so the browser runs genuine LightGBM inference instead of the current heuristic proxy.
  • Align the class-index mapping. The Python training script and the in-browser classifier order the four classes differently in a couple of places; worth auditing end-to-end once real inference replaces the proxy.
  • Expand the allowlist model. A hardcoded domain list doesn't scale; a Tranco/Majestic top-N list or a small on-device cache would generalize better.
  • Add a feedback loop. Let a user flag a wrong block/miss from the popup and use that signal to retrain periodically.
