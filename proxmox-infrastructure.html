Building a Fully Automated, Highly Available IT Infrastructure on Proxmox VE

A final-year project write-up — how we designed, deployed, and validated a production-grade virtualized infrastructure where a single git push provisions machines, configures services, runs tests, and rolls back on failure, with no manual intervention.

The problem

Most SMEs still run one service per physical server. It's simple, but it comes with a specific set of costs that compound over time: servers sit at 10–20% utilization most of the day, a single hardware failure takes the whole service down with it, provisioning a new server takes days, and nobody notices a problem until a user complains.

The usual next step — buying a commercial virtualization platform — solves some of this, but trades it for vendor lock-in and per-node licensing that can run into thousands of euros for the features (HA, live migration) that actually justify the switch. Public cloud solves the elasticity problem but raises new ones: data sovereignty, a hard dependency on internet connectivity, and long-term costs that are hard to predict.

The brief for this project, done during a stage at Prologic Tunisie, was to prove a specific claim: that an open-source stack alone — no commercial hypervisor, no cloud — can deliver a highly available, fully automated, centrally supervised production infrastructure.

What we built

A two-node Proxmox VE cluster forms the compute layer, hosting a mix of Windows Server VMs (Active Directory, WDS), Linux VMs, and LXC containers for lightweight services (DNS, NFS, internal apps). Shared storage sits on a NAS in RAID 5, exported over NFS so both nodes can see the same VM disks — the prerequisite for live migration and HA failover.

git push
   → validate.yml   (Terraform fmt/validate, ansible-lint)
   → deploy.yml     (terraform apply → VMs, then LXC)
   → configure.yml  (Ansible playbooks per service role)
   → tests.yml      (connectivity + service checks)
   → notify.yml     (Slack: success/failure + log link)

That pipeline runs on GitHub Actions, but the actual terraform apply and Ansible runs can't happen on GitHub's cloud runners — they have no route into a private LAN. So a self-hosted runner, itself just an LXC container on the cluster, sits as the only bridge: it opens an outbound connection to pick up jobs, then executes locally against the private network. Credentials never leave the perimeter; only validation jobs (pure syntax checks) run on GitHub's public runners.

On top of that: Zabbix 7.0 watches every host and triggers two things — an alert to Slack/email, and, for load thresholds specifically, a repository_dispatch call back into the same GitHub Actions pipeline, which resizes the affected VM's CPU/RAM via Terraform. Veeam Backup & Replication runs a 3-2-1 backup policy with GFS retention. pfSense segments the network into four VLANs (admin, services, monitoring, database) under a default-deny policy, with pfBlockerNG blocking a live list of ~16,700 known-malicious IPs at the WAN edge.

Testing it properly

The validation strategy leaned on forcing real failures rather than trusting the design on paper — the same principle as any good security or reliability tool: a claim is only as good as the failure you actually caused and recovered from.

Config-drift and idempotence testing. Every Ansible playbook was re-run against an already-configured host to confirm changed=0 — proof that CI can safely re-apply configuration without side effects, which matters because the pipeline re-runs on every push, not just the first one.

Hard node failure, not a graceful shutdown. To test HA, node1 — which at the time hosted the entire workload — was killed abruptly, simulating a power loss rather than a clean shutdown. Corosync detected the lost heartbeat, the HA manager fenced the dead node, and every VM and container was re-instantiated on the surviving node automatically. According to the project's own measurements, detection took about 12 seconds and full service recovery (RTO) landed around 42 seconds — and because Qdevice holds the deciding vote in this two-node setup, the cluster never split-brained during the test.

Load-triggered auto-scaling, closed loop. stress-ng was used to pin 4 CPU cores on the database VM for 120 seconds. Zabbix caught the threshold breach, fired the alert, and — separately — the scaling workflow resized a different, genuinely idle VM down via the same Terraform-backed pipeline, proving the loop runs in both directions (scale up on real load, scale down on real idleness) without a human touching the console.

Full disaster-recovery restore, not just a backup job. The strongest test here: rather than trusting that a backup would restore, the team deleted a 160 GB production VM outright and restored it from Veeam to its original location — same network bridge, same storage backend — and confirmed it came back fully functional, not just "present."

Being honest about what's a lab simplification

A few things are worth stating plainly, the same way the underlying report does — because a design that's honest about its shortcuts is more trustworthy than one that isn't.

The network is flatter than the VLAN diagram suggests. The pfSense segmentation (VLANs 10/20/30/40, each with its own subnet) is real and its firewall rules are enforced. But the Proxmox management network itself — where the VMs' actual IPs live — runs on a single flat /24 (192.168.1.0/24), not one subnet per VLAN. This was a deliberate simplification for the lab phase, not an oversight, but it does mean the full "one VLAN per trust zone" model isn't end-to-end yet for the compute layer itself.

"No downtime" resize deserves a closer look. Proxmox can hot-plug RAM and, with the right guest agent and kernel support, additional vCPUs — but this isn't automatic for every OS/config combination, and a Windows guest in particular often needs a reboot to recognize new vCPUs even if the hypervisor-side resize itself is instant. Before repeating "zero-downtime auto-scaling" as a blanket claim, it's worth measuring actual in-guest service continuity during a scale event, not just confirming the Terraform apply succeeded.

Veeam Community Edition has a workload ceiling. It's free and genuinely full-featured for a lab or small deployment, but it caps at a limited number of protected workloads — worth flagging if this design is pitched as directly production-ready for a larger org rather than as a proof of concept sized for a 10–15 VM cluster.

Validation was manual, not itself automated. The recipe of tests (kill the node, run stress-ng, delete the VM) is rigorous, but it was executed by hand and documented via screenshots rather than wired into the CI pipeline as repeatable chaos-engineering jobs. Turning "we did this test once and it passed" into "this test runs on every merge to main" is the natural next step for a project that's already this automation-minded everywhere else.

What's next

  • Kubernetes for the application layer — move application workloads from VMs to orchestrated microservices once the infrastructure layer below is this solid.
  • Automate the chaos tests themselves — turn the manual HA-failover and restore drills into scheduled or CI-triggered jobs, so "the cluster survives a node failure" is continuously re-verified, not verified once.
  • AIOps-style predictive scaling — replace the fixed CPU/RAM thresholds with a model that scales ahead of a load spike rather than reactively after Zabbix already caught it.
  • Multi-site / hybrid-cloud extension — the natural path if the cluster ever needs elasticity beyond the two physical nodes on hand.
